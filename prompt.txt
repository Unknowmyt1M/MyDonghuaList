🧠 2. Most Important Decision: Data Architecture

Main external API ko TrackMyDonghua ka database nahi banaunga.

Instead:

External Sources
      ↓
Data Ingestion Worker
      ↓
Normalization
      ↓
TrackMyDonghua PostgreSQL
      ↓
Frontend

Yaani external APIs source of truth nahi, balki data providers honge.

This gives us:

faster pages

reliable search

historical data

stable IDs

less API dependency

better recommendations

release tracking

user-generated metadata

ability to change providers later

Aur ye especially important hai because AniList explicitly API ko backup/data-storage service ki tarah use karne aur mass collection ko prohibit karta hai. (Anilist)

📚 3. Donghua Data Sources

Primary approach

Humein licensed/permission-compatible sources choose karne chahiye.

Potential sources ko adapter architecture ke through connect karenge:

DataProvider
├── ProviderA
├── ProviderB
├── ProviderC
└── ManualAdminData

Har provider ka output:

NormalizedTitle
NormalizedSeason
NormalizedEpisode
NormalizedPerson
NormalizedGenre

Then database mein merge.

TMDB

TMDB useful secondary metadata provider ho sakta hai.

It provides TV-series details and season/episode-level information through its API. (The Movie Database (TMDB))

But TMDB ko sole donghua database nahi maanunga. Coverage and metadata quality Chinese animation ke liye verify karni padegi.

Also API requests ko server-side cache karna better hai; TMDB currently roughly ~40 requests/sec range mein upper limits maintain karta hai and 429 responses respect karne chahiye. (The Movie Database (TMDB))

🔒 6. RLS - Very Important

Every user-owned table should have policies like:

user_id = auth.uid()

Example:

user_titles

User:

✅ own watchlist read
✅ own watchlist create
✅ own watchlist update
✅ own watchlist delete

Cannot:

❌ modify another user's list

Supabase explicitly recommends RLS on exposed tables; without appropriate policies, client-side access can expose or modify data incorrectly. (Supabase)

⚠️ One Big Thing I Would NOT Do

Random scraping + random anime APIs ko frontend se directly call nahi karunga.

That creates:

API dependency
+
rate limits
+
CORS problems
+
inconsistent IDs
+
data duplication
+
legal/licensing headaches
+
slow UI

Instead:

Provider → ingestion → normalized DB → frontend.

That's the difference between a demo and an actual platform.
